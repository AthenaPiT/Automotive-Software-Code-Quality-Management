Software Code Quality Management Procedure

Classification Internal​

Document use note: This procedure is a customizable process template. Tailor it to the organization's quality management system, product architecture, safety and cybersecurity classifications, customer-specific requirements, and applicable regulations before release. It does not by itself establish compliance or replace project-specific safety, cybersecurity, or legal obligations.

1. Purpose​

This procedure defines a controlled, evidence-based method to plan, implement, measure, review, improve, and release software code quality for automotive electronic software. It establishes common controls across the software lifecycle so that source code is maintainable, analyzable, testable, secure, robust, traceable, and suitable for its intended use.

The procedure is intended to prevent defects early, detect defects systematically, manage exceptions transparently, and provide objective evidence for engineering and release decisions.

2. Scope​

This procedure applies to:

  • New software development, maintenance, refactoring, porting, integration, and defect correction.
  • Application software, basic software, firmware, bootloaders, drivers, middleware, diagnostics, communication stacks, and relevant scripts or generated code.
  • Internally developed software, supplier-delivered software, and open-source software (OSS) incorporated into a product.
  • Development branches, integration branches, release candidates, and production maintenance branches.
  • Static analysis, coding-rule compliance, code review, unit-level verification, code coverage, build quality, defect management, and quality reporting.

Project plans shall identify any software or generated artifacts that are excluded from specific controls and document the rationale, risk assessment, compensating controls, and approval.

3. References and governing requirements​

Use the applicable editions and contractual versions of the following as relevant to the product and organization:

  • Automotive SPICE (ASPICE): software engineering, verification, validation, configuration management, problem resolution, and quality assurance process expectations.
  • ISO 26262: functional safety lifecycle and software-related work products for road vehicles when functional safety applies.
  • ISO/SAE 21434: cybersecurity engineering for road vehicles when applicable.
  • IATF 16949 / ISO 9001: organizational quality management system requirements, where applicable.
  • MISRA C, MISRA C++, AUTOSAR C++14, CERT C/C++, or other approved coding standards: select according to language, architecture, customer requirements, and project risk.
  • ISO/IEC 5055 or other approved source-code weakness taxonomies: where adopted by the organization.
  • Customer-specific requirements, internal engineering standards, tool qualification/assessment requirements, and product-specific safety and cybersecurity plans.

The project shall maintain a controlled Applicable Standards and Requirements Register listing the exact edition, customer deviations, tailoring decisions, and owner. If requirements conflict, the project shall resolve the conflict through the organization's requirements and compliance process rather than silently choosing one.

6. Management principles​

  1. Prevention before detection: use clear requirements, architecture, coding standards, and peer review to avoid defects.
  2. Automation by default: execute repeatable checks in the CI pipeline and preserve their results.
  3. Risk-based rigor: apply stronger scrutiny to safety-, security-, and mission-critical components without relaxing mandatory requirements.
  4. Traceability: link requirements, change requests, code changes, reviews, analysis results, tests, defects, and releases.
  5. No silent exceptions: every accepted violation or unmet threshold requires a documented disposition and authorized approval.
  6. Reproducibility: record tool versions, rule sets, configurations, build identifiers, and source revision for material results.
  7. Continuous improvement: use trends, escaped defects, root-cause analysis, and lessons learned to improve standards and practices.

7. Process overview​

The process follows these stages:

  1. Plan code quality and define acceptance criteria.
  2. Establish coding standards, toolchain, and baseline metrics.
  3. Implement changes using controlled branching and secure development practices.
  4. Perform peer review and automated analysis.
  5. Execute unit verification and relevant coverage analysis.
  6. Triage findings, correct defects, and manage deviations.
  7. Evaluate quality gates and residual risks.
  8. Approve and baseline the release.
  9. Monitor field issues and improve the process.

A project may integrate these activities into its agile iteration, V-model, continuous integration, or supplier workflow, provided that required controls and evidence remain demonstrable.

8. Procedure​

8.1 Plan code quality​

At project initiation and at significant planning changes, the Software Development Lead shall create or update a Software Code Quality Plan. The plan shall define:

  • Applicable components, languages, repositories, generated code, and supplier code.
  • Applicable coding standards, rule sets, language versions, and approved deviations.
  • Component criticality and required verification rigor.
  • Toolchain and execution environments, including versions and configuration control.
  • Required code reviews, static-analysis checks, unit tests, coverage measures, and security checks.
  • Quality metrics, thresholds, reporting frequency, and owners.
  • Quality gates for merge, integration, release candidate, and production release.
  • Defect severity definitions, triage targets, escalation paths, and closure criteria.
  • Evidence retention location and retention period.
  • Responsibilities and approval authorities.
  • Tailoring decisions, exclusions, and compensating controls.

SQA shall review the plan for completeness and process consistency. The project authority shall approve it before the first controlled integration, or at the earliest project milestone defined by the quality management system.

8.2 Define and maintain coding standards​

The Software Development Lead, supported by the Software Architect and safety/security specialists as applicable, shall select a language-specific coding standard and a controlled rule set.

The project rule set shall address, as applicable:

  • Language subset and prohibited or restricted language features.
  • Type safety, integer conversions, overflow, pointer use, memory ownership, and bounds checking.
  • Initialization, lifetime, resource management, error handling, and defensive programming.
  • Concurrency, interrupt context, reentrancy, race conditions, and deadlock risks.
  • Timing, stack, memory, and execution determinism.
  • Interface contracts, API usage, and data validation.
  • Logging and diagnostics without leaking secrets or sensitive data.
  • Secure coding issues such as injection paths, unsafe functions, hard-coded credentials, and cryptographic misuse.
  • Readability, naming, function size, complexity, duplication, and modularity.
  • Rules for macros, preprocessor conditions, compiler extensions, and generated code.

For each mandatory rule, record a unique rule ID, description, rationale, applicability, severity, verification method, and deviation policy. The coding standard and tool rule configuration shall be version-controlled. Changes to the rule set shall be reviewed for impact, trialed where practical, and approved before broad adoption.

8.3 Establish the baseline and development environment​

Before controlled development or integration, Configuration Management shall establish:

  • Repository ownership, access controls, protected branches, and merge permissions.
  • Branching, commit-message, pull-request, and tagging conventions.
  • Approved compiler, linker, build system, analysis tools, test tools, and versions.
  • Reproducible build configuration and dependency management.
  • CI pipeline configuration, quality-gate implementation, and artifact retention.
  • Versioned analysis rules, suppressions, and baseline findings.
  • Traceability conventions for requirements, change requests, defects, commits, and test results.

Tool updates that can affect results shall be impact-assessed and recorded. Where a tool is relied on to satisfy a safety-related or otherwise regulated objective, tool confidence, qualification, validation, or assessment shall be handled according to the applicable project plan and standard.

8.4 Implement code changes​

For every change, the developer shall:

  1. Confirm the approved requirement, defect, or change request and understand acceptance criteria.
  2. Assess affected components, interfaces, dependencies, safety impact, cybersecurity impact, and compatibility.
  3. Implement the smallest coherent change that meets the requirement.
  4. Follow the approved coding standard and avoid unrelated modifications.
  5. Add or update unit tests and relevant robustness or negative tests.
  6. Update comments, interface documentation, design records, and traceability where needed.
  7. Run local build, formatting, static-analysis, and unit-test checks required by the project.
  8. Review all new warnings and findings; do not suppress findings merely to obtain a clean report.
  9. Submit the change with a description, test evidence, known limitations, and linked work items.

Generated code shall be managed under a defined policy identifying the generator, version, configuration, ownership, permitted manual edits, and verification approach. Third-party and OSS code shall follow the project's supplier, vulnerability, licensing, and compliance processes.

8.5 Perform peer code review​

Every non-trivial production code change shall receive documented peer review before merge. The project may define narrowly scoped exceptions for trivial changes, generated files, or emergency fixes, but exceptions shall be justified, risk-assessed, and subject to retrospective review where appropriate.

Reviewers shall consider at least:

  • Requirement correctness and traceability.
  • Logic, boundary conditions, error paths, and failure handling.
  • Compliance with coding rules and project architecture.
  • Memory safety, resource lifecycle, concurrency, timing, and determinism.
  • Safety mechanisms and safe-state behavior, where applicable.
  • Attack surface, input validation, privilege boundaries, and secret handling, where applicable.
  • Test adequacy, test readability, and coverage of changed behavior.
  • API/interface compatibility and impact on dependent components.
  • Maintainability, complexity, duplication, and clarity.
  • Whether analysis warnings, suppressions, and deviations are justified.

The review record shall identify the change, reviewer(s), review date, findings, dispositions, and approval status. The author shall resolve or formally disposition each finding. The author shall not approve their own change where independent review is required by project rules.

8.6 Run automated quality checks​

The CI pipeline shall execute the checks defined in the Software Code Quality Plan. Depending on component risk, these may include:

  • Build and compiler diagnostics, with warnings treated according to the approved policy.
  • Formatting and basic source hygiene checks.
  • Coding-standard compliance and static analysis.
  • Data-flow, control-flow, defect-pattern, and security analysis.
  • Unit tests and regression tests.
  • Statement, branch, condition, or modified-condition/decision coverage where required.
  • Dependency, OSS license, and known-vulnerability checks.
  • Binary, memory, stack, timing, or other resource checks where required.
  • Detection of secrets, prohibited APIs, and unsafe configuration.
  • Reproducible build and artifact-integrity checks.

The pipeline shall fail or block the relevant transition when a mandatory gate fails, unless an approved exception mechanism explicitly permits the transition. A green pipeline shall not be interpreted as proof that software is defect-free; engineering review and verification remain necessary.

8.7 Manage static-analysis findings​

All findings shall be triaged using the approved workflow. The team shall classify each finding as:

  • Confirmed defect: correct the code and add regression protection where appropriate.
  • Valid rule violation without demonstrated defect: correct it or request a formal deviation.
  • False positive: document technical evidence and obtain the required review/approval.
  • Not applicable: document why the rule does not apply to the code context and obtain approval where required.
  • Duplicate: link to the primary finding while retaining traceability.
  • Deferred: record risk, rationale, owner, due date, and approval. Deferral is not closure.

Each finding shall have a unique identifier, location, rule ID, severity, status, owner, target date, disposition, and evidence. Suppressions shall be as narrow as possible, include a reason and reference to the approved disposition, and be periodically revalidated. Blanket suppression or disabling a rule set to bypass a gate is prohibited unless formally approved as a controlled tool-configuration change.

8.8 Verify code changes and coverage​

Verification shall be proportional to the change and component risk. At minimum, the developer or verification owner shall demonstrate that:

  • The change builds in the controlled environment.
  • Unit tests cover normal, boundary, error, and relevant robustness behavior.
  • Changed behavior is tested and regression risk is addressed.
  • Tests are repeatable and their results are linked to the relevant source revision.
  • Coverage results meet project-defined thresholds where coverage is required.
  • Uncovered code and unreachable code are analyzed and dispositioned.
  • Mocks, stubs, test harnesses, and instrumentation do not invalidate the interpretation of results.

For safety-related software, coverage criteria and structural coverage analysis shall be selected according to the applicable safety plan and ISO 26262 requirements. Coverage thresholds shall not be treated as a substitute for test quality, requirements coverage, or analysis of uncovered behavior.

8.9 Manage defects and quality risks​

Defects shall be logged in the approved defect or problem-resolution system and classified by severity, priority, affected release, component, and safety/security relevance.

The defect record shall include reproducible evidence where possible, expected versus actual behavior, environment and version, impact assessment, owner, containment, root cause when required, corrective action, verification evidence, and closure approval.

For high-severity, safety-related, security-related, recurring, or release-blocking defects:

  1. Notify the Software Development Lead and relevant quality, safety, security, and project authorities promptly.
  2. Assess exposure across branches, variants, platforms, and released products.
  3. Contain the issue and prevent unintended integration or release.
  4. Perform root-cause analysis proportional to risk and recurrence.
  5. Define corrective and preventive actions, including tests or rules that prevent recurrence.
  6. Verify the fix and affected regression scope.
  7. Escalate unresolved risk using the project escalation procedure.

A defect shall not be closed solely because code has been changed; required verification and traceability must be complete.

8.10 Control deviations and waivers​

A deviation request shall be raised before accepting a known nonconformance, except for a documented emergency process approved by the organization. Each request shall contain:

  • Deviation ID and affected rule/criterion.
  • Affected files, components, variants, and releases.
  • Technical rationale and why compliant alternatives are unsuitable.
  • Functional, safety, cybersecurity, reliability, maintainability, and customer impact analysis, as applicable.
  • Risk assessment and evidence supporting the assessment.
  • Compensating controls and verification activities.
  • Scope, owner, approver, validity period, expiry/review date, and closure conditions.
  • Customer or external approval when contractually or legally required.

The author shall not be the sole approver. Safety or cybersecurity authorities shall participate when their domain may be affected. A deviation does not waive applicable law, regulation, customer requirements, or mandatory safety obligations. Expired deviations shall be treated as nonconformities until renewed or closed.

8.11 Conduct quality reviews and reporting​

The Software Development Lead shall review code-quality status at the cadence defined in the project plan, and at minimum at significant integration and release milestones. SQA shall independently sample evidence and report process nonconformities.

Reports shall include:

  • Mandatory gate pass/fail status.
  • Open findings by severity, age, component, and rule category.
  • Trend of newly introduced versus resolved findings.
  • Review completion and review-finding closure.
  • Unit-test results and required coverage status.
  • Defect escape rate and recurring root causes.
  • Approved deviations, expired deviations, and suppressions.
  • OSS compliance and dependency vulnerability status where applicable.
  • Resource, complexity, duplication, and maintainability trends where adopted.
  • Risks, owners, due dates, and decisions required.

Metrics shall be interpreted in context. Teams shall not optimize a metric by suppressing findings, reducing test scope, splitting defects, or changing thresholds without controlled approval.

8.12 Release readiness and approval​

Before a release candidate is approved, the responsible team shall confirm that:

  • The release source revision and build artifacts are uniquely identified.
  • Required code reviews are complete and approved.
  • Mandatory CI checks and quality gates pass.
  • No unresolved release-blocking defects remain.
  • Remaining findings and deviations have documented, authorized dispositions.
  • Required unit verification and coverage objectives are met or formally dispositioned under applicable rules.
  • Safety and cybersecurity work products and approvals are complete where applicable.
  • OSS inventory, license obligations, and vulnerability dispositions are complete under the relevant process.
  • Traceability and evidence are complete and retrievable.
  • Known residual risks are accepted by the authorized decision-maker.
  • Release notes and relevant limitations are documented.

The Release Authority shall record the decision, evidence reviewed, accepted residual risks, and any conditions. A failed mandatory gate shall not be overridden informally. Emergency releases shall follow the approved emergency change process, including risk acceptance, minimum required checks, post-release verification, and retrospective review.

8.13 Post-release monitoring and improvement​

After release, the project shall monitor field defects, warranty data, customer reports, security advisories, supplier notifications, and production incidents relevant to code quality.

For significant issues, the team shall assess affected versions and variants, determine containment or corrective action, and feed lessons learned into coding rules, static-analysis configurations, test cases, review checklists, architecture guidance, and training.

At planned intervals, the process owner shall review trends and determine whether quality thresholds, tooling, training, or workflow changes are needed. Improvements shall be tracked to completion and their effectiveness evaluated.

9.1 Example threshold policy​

The project shall set numeric thresholds based on baseline data, product risk, and customer requirements. The following are examples only and must not be adopted without project approval:

  • Zero open critical or blocker findings at merge and release.
  • Zero unresolved mandatory coding-rule violations unless a valid, approved deviation is permitted.
  • 100% completion of required peer reviews.
  • 100% pass rate for mandatory pipeline checks on the release baseline.
  • Unit-test and structural coverage targets defined by component risk and applicable safety plan.
  • No expired deviations at release.
  • All high-severity defects assigned an owner and containment/decision plan within the project-defined response time.

A threshold shall specify the measurement method, scope, data source, responsible owner, review cadence, and permitted exception process.

11. Escalation​

Escalation shall follow the project's Defect Escalation and Deviation Procedure. At minimum:

  • Immediate escalation: suspected safety impact, exploitable vulnerability, critical production failure, or credible risk of violating a safety goal or legal/customer obligation.
  • Prompt engineering escalation: release-blocking defect, repeated critical rule violation, failed mandatory gate, or deviation without required approval.
  • Management escalation: overdue high-risk corrective action, unresolved cross-team ownership, recurring quality deterioration, or resource constraints that threaten mandatory verification.
  • Release hold: when required evidence is missing, a mandatory gate fails, a deviation is invalid/expired, or residual risk lacks authorized acceptance.

Escalation records shall identify the issue, affected scope, containment, accountable owner, decision deadline, and final disposition.

12. Records and evidence retention​

The following records shall be controlled under the organization's document and configuration management rules:

  • Software Code Quality Plan and revisions.
  • Coding standards, rule catalogues, and tool configurations.
  • Source revisions, change requests, pull requests, and review records.
  • CI pipeline results, build logs, static-analysis reports, test results, and coverage reports.
  • Finding and defect records, root-cause analyses, corrective actions, and closure evidence.
  • Deviation/waiver requests, approvals, expiry dates, and reassessments.
  • Quality dashboards, milestone reports, gate decisions, and release approvals.
  • Supplier evidence, OSS inventory and compliance records, and vulnerability dispositions.
  • Training and process-improvement records where required.

Retention periods shall meet legal, regulatory, customer, safety-case, cybersecurity, and organizational requirements. Evidence shall be retrievable by release baseline and protected against unauthorized modification.

13. Training and competency​

Personnel performing code development, review, analysis, testing, and approval shall receive role-appropriate training on:

  • Applicable coding standards and project-specific rules.
  • Tool usage and interpretation of results.
  • Review and defect-management practices.
  • Safety and cybersecurity obligations relevant to their work.
  • Deviation handling, evidence requirements, and escalation paths.

Competency expectations and training records shall be maintained according to the organization's training process. Significant changes to standards or tools shall trigger an impact assessment for retraining.

14. Process compliance and audit​

SQA or an authorized assessor shall periodically sample projects and releases to verify that:

  • Planned activities were performed.
  • Evidence is complete, consistent, and traceable to the source baseline.
  • Required independence and approval rules were followed.
  • Findings and deviations are controlled and not improperly suppressed.
  • Quality gates were applied consistently.
  • Corrective actions were completed and effectiveness was checked.

Nonconformities shall be recorded and managed through the organization's corrective-action process. Audit sampling shall be risk-based and include high-criticality components, recurring problem areas, and releases with significant deviations.

15. Tailoring rules​

Tailoring is permitted only when documented and approved before the affected activity, unless an approved emergency process applies. Each tailoring decision shall identify:

  • Requirement or activity being tailored.
  • Reason and affected scope.
  • Risk and impact analysis.
  • Alternative or compensating control.
  • Approver and validity period.
  • Evidence needed to show the tailored process remains effective.

Tailoring shall not be used to bypass mandatory legal, regulatory, contractual, safety, or cybersecurity requirements.

Appendix B --- Code Review Checklist

Use the checklist for each applicable change. Mark Pass, Fail, N/A, or Action required; explain all Fail and N/A responses where required.

  • Requirement or defect link is valid and acceptance criteria are clear.
  • Change is limited to the intended scope; unrelated modifications are justified.
  • Logic, boundary conditions, invalid inputs, and error paths are handled.
  • Data types, conversions, bounds, pointer use, and memory/resource lifecycle are safe.
  • Concurrency, timing, interrupt behavior, and reentrancy are addressed where applicable.
  • Interfaces, dependencies, compatibility, and architectural constraints are respected.
  • Applicable safety mechanisms and safe-state behavior are preserved.
  • Security-sensitive inputs, permissions, secrets, and error messages are handled appropriately.
  • Approved coding standard is followed; findings and suppressions are reviewed.
  • Tests cover normal, boundary, negative, and relevant regression scenarios.
  • Test results correspond to the reviewed source revision.
  • Documentation, traceability, and diagnostic behavior are updated as needed.
  • Deviations are approved, scoped, and within validity.
  • Reviewer findings are resolved or formally dispositioned.
